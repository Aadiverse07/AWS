Jarvis Decider MVP: Architecture, Roadmap
and Folder Structure
Trimmed plan for the AWS Agent Experience Hackathon (Strands Decider 2B). It replaces
the earlier long plan. Nothing here assumes you already have a finished Jarvis or your own
MCP server.
1. The MVP in one page
What it is. A decision-first agent. At each step a small, fast decision model (Strands
Decider 2B) chooses among options, and a larger LLM is called only when the Decider's
confidence is low or when real writing or planning is needed.
Use case. A maintainer triage agent for solo open-source maintainers and student dev
teams: read GitHub issues, decide what is actionable, research a fix, and draft a plan.
What you actually build (the four things judges score):
1. The decision engine: contract, thresholds, escalation (about 200 lines).
2. A thin orchestrator loop that runs one decision step after another.
3. The 50-task eval set and runner, on frozen fixtures so runs are free and reproducible.
4. The trace view and the comparison chart.
What you reuse (do not write):
Agent framework: Strands Agents SDK (open source). Verify its current MCP client
support in the docs.
GitHub tools: GitHub's official MCP server. Verify current install steps and token
scopes.
Web fetch tools: an existing maintained MCP fetch server (check which ones in the
official modelcontextprotocol/servers repo are still maintained).
Decider model: open weights from Hugging Face (check the model card for the exact
input and output format).
Planner and escalation LLM: a small local model through Ollama.
Backend and storage: FastAPI and SQLite.
Dashboard: Streamlit.

3. The decision contract
Decider scores a list of options you supply. It does not plan or generate text. So every use
follows one contract:
DecisionRequest = { decision_id, question, context, options[], run_id, step }
DecisionResult  = { chosen, scores, confidence, latency_ms, backend,
                    escalated, final_choice, final_source }
Escalation rule. If confidence >= threshold[decision_id] , use the Decider's choice.
Otherwise send the same request to the LLM and use its answer. Thresholds live in
configs/thresholds.yaml  and are tuned from eval data.

4. Architecture
 Streamlit dashboard: run, decision trace, eval results
            |
   FastAPI (or direct Python call for the demo)
            |
   Orchestrator loop (Strands Agents)
     1. intake -> planner LLM writes a plan of at most 5 steps
     2. for each step:
          D1 agent   -> shortlist tools -> D2 tool
          D5 safety  -> execute via MCP (read-only) or draft
          D4 result check -> retry / replan / next
          any decision below threshold -> escalate to LLM
     3. synthesizer LLM writes the final report and draft comment
            |
   Existing MCP servers: GitHub (official), web fetch
            |
   Trace log (JSONL + SQLite) -> dashboard + eval harness
Components
Decision engine. Builds the request, calls the active backend, applies the threshold,
escalates, and writes a trace event for every decision.
Orchestrator. Asks the planner LLM for a short structured plan, then runs the step
loop. No playbooks in v1.
Agents. Each is just a system prompt, an allowed-tool list and a result check.
Shortlister. Keyword/BM25 scoring plus the agent's allow-list narrows all tools to 5 to 8
before D2.
ID Question Options
D4 Did the tool result satisfy the step? satisfied, retry, replan
D5 Is this action safe to run now? execute, draft_only, block
D6 Should this go to the big LLM? stay_small, escalate

===== PAGE 4 =====
Guardrails. A small policy file lists tools that can never auto-run. Tool output is
wrapped as untrusted data before any LLM sees it, and the GitHub token is read-only
and redacted in traces.
Synthesizer. One LLM call that turns evidence into a ranked answer with issue
numbers and links. Comment drafts are shown, never posted.
5. Free stack and upgrade path
Cost safety (build on day one): default is COST_MODE=free . COST_MODE=production  also
requires ALLOW_PAID=true , otherwise startup fails. Check current AWS pricing and free-
tier terms yourself and set a budget alert before enabling any AWS service.
6. Evaluation (your differentiator)
Dataset. 50 tasks in eval/datasets/tasks_v1.jsonl . Each has an input, a frozen fixture
repo, the expected agent and tool per step, success checks (for example "must name
issue #14"), and a flag for tasks that must be drafted only or refused.
Metrics. Agent accuracy, tool accuracy, task success, escalation rate, decision latency
(p50, p95), LLM tokens per task, unsafe actions executed (target 0).

8. Roadmap
Assumes today is Oct 8 and the build window is Oct 16 to 23. Confirm in the official rules
whether pre-work before Oct 16 is allowed. If not, treat Phase 0 as research and design
only.
Phase 0: Prep (Oct 8 to 15)
Oct 8 to 9, the gate. Get Decider running locally and make one decision from the model
card's format. Measure latency on your machine. If it will not run, use a free Colab or
Kaggle GPU, and develop against the mock  backend meanwhile. Also run the GitHub
MCP server and make one tool call.
Oct 10 to 11. Write the 50 eval tasks with expected agent, tool and outcome labels.
Build one small frozen fixture repo.
Oct 12 to 13. Skeleton: config, cost guard, trace schema, DeciderProvider  interface
plus mock  and local_hf , MCP client connecting to existing servers.
Oct 14. Choose and test the local planner LLM. Confirm it fits your hardware.
Oct 15. Read the official rules and judging criteria. Pick one AWS touchpoint. Freeze
scope.
Phase 1: Build (Oct 16 to 23)
Oct 16 to 17. One task end to end (plan, D1, D2, execute, D4, synthesize) with traces.
Oct 18. Second agent, shortlister, D5 safety, D6 and threshold escalation.
Oct 19 to 20. Run the full eval, the three-way comparison and threshold sweep. Fix the
worst failure categories.
Oct 21. Streamlit trace timeline and eval page.
Oct 22. Deploy the smallest meaningful AWS piece (for example Bedrock as the
escalation LLM, or one hosted endpoint). Record the demo.

9. Demo script (3 minutes)
1. 0:00 One-sentence problem and a messy issue list.
2. 0:20 Type the task and show the live trace: decisions, confidences, one visible
escalation.
3. 1:10 Show the drafted comment, not posted.
4. 1:30 Eval page: three-way comparison, latency and token savings.
5. 2:15 One failure and the fix that improved the score.
6. 2:40 Flip the config to the AWS-backed run and close on the upgrade path.
